# Benchmark snapshot — Netty-Loom vs Tomcat

- **Date:** 2026-08-09 (commit `734ef88`)
- **Machine:** `Darwin 25.5.0 arm64`, Apple M1 Pro, 16 GB, JDK 25.0.2 (Temurin), k6 v1.4.2
- **JVM flags (identical for all targets):** `-XX:+UseG1GC -Xmx2g -XX:NativeMemoryTracking=summary`
- **Logical cores:** 8 (client and server share this box — see CPU efficiency below)
- **Tomcat connector:** `max-connections=20000` on both Tomcat targets, and `threads.max=20000` on the virtual target (platform keeps the default `threads.max=200` — the thread-per-request pool under test). Raised above the connection count so Tomcat's default `max-connections=8192` accept ceiling — which `spring.threads.virtual.enabled` does not touch — isn't the confound.
- **High-concurrency connections (VUs):** 10,000
- **Workload:** `GET /work` → `Thread.sleep(50)` (simulated 50ms blocking DB call); keep-alive on, so 1 VU ≈ 1 connection ≈ 1 in-flight request.

> Normally generated by `scripts/run-all.sh`; this copy was transcribed by hand, because the 2026-08-09 sweep's raw exports did not survive to be committed. Re-running the harness is the only way to regenerate it. **One forward pass, no crossover** — nothing here is order-controlled, and two cells the transcription could not carry are marked `—`. Full analysis, caveats and cross-sweep comparison in [`docs/benchmarks/2026-08-09/COMPARISON.md`](../../docs/benchmarks/2026-08-09/COMPARISON.md).

## Headline

At **10,000 concurrent blocking connections**:

- **CPU efficiency:** Netty-Loom 2.2 cores → 20,336 req/s per core vs Tomcat+VT 3.2 cores → 8,322 req/s per core.
- **Throughput:** Netty-Loom 44,584 req/s vs Tomcat+VT 26,819 vs Tomcat-platform 3,663 req/s.
- **Tail latency (p99):** Netty-Loom 420 ms vs Tomcat+VT 2,409 ms (5.7×) vs Tomcat-platform 2,831 ms (6.7×).
- **Error rate:** Netty-Loom 0.00% vs Tomcat+VT 0.00% vs Tomcat-platform 0.00%.

**Does flipping `spring.threads.virtual.enabled=true` on Tomcat close the gap?** **It depends on the connection count, and the answer is only measured at two of them.** At 10,000 connections, no — Netty-Loom leads on throughput and p99 tail at an equal 0.00% error rate. At **2,000** connections the flag closes it entirely: 30,885 vs 30,128 req/s (+2.5%, inside this harness's ±11% noise floor) with identical p99, 93.0 vs 93.2 ms — measured in the 2026-08-01 sweep, which is the only one to run that load level. Any claim from this file carries the connection count or it is not a claim.

**Is the throughput edge structural or a single-box contention artifact?** Structural: Netty-Loom does more work *per core* (20,336 vs 8,322 req/s/core, 2.4×) while burning **less** CPU in absolute terms (2.19 cores vs 3.22), so the win isn't merely from grabbing cores k6 left idle. Off-box, raw per-request efficiency may compress, but a per-core advantage like this should persist. The 2026-08-01 sweep found this figure flat from 2,000 to 10,000 VUs (~18,200–19,000) while Tomcat+VT's halved; this sweep measured only the 10,000-VU half, so the flatness rests on that sweep alone.

> Single-box loopback numbers: the k6 client contends with the server for CPU, so absolute latencies are inflated and the comparison is relative, not absolute. The CPU efficiency table is the discriminator for what survives off-box. See [README](../README.md) caveats.

| Target | `/work` (req/s) | `/work-secured` (req/s) | Δ throughput (higher is better) | `/work` p99 (ms) | `/work-secured` p99 (ms) | Δ p99 (lower is better) |

| Tomcat, virtual threads | 26819 | 22446 | −16.3% | 2408.9 | 3407.6 | +41.5% |

Δ is scenario 3 against scenario 2 on the *same* target, jar and run, so it isolates the Spring Security filter chain plus one session lookup per request. `/ping` and `/work` sit outside the chain (`securityMatcher` scopes it to the secured paths), so scenarios 1 and 2 stay broadly comparable to the pre-Security snapshot — they still pay `DelegatingFilterProxy` and the firewall on every request, which is small but not zero. Read the Δ with the run order in mind: scenario 3 always runs second, on a JVM that has just served the scenario-2 plateau, and run-to-run noise on this harness is around ±11% — a Δ inside that band is not a measurement. The two that clear it, −13.1% and −16.3%, are within a point and a half of each other: the filter chain costs this library no more than it costs Tomcat+VT.

## CPU efficiency (server-side, during the 10,000-connection run)

| Target | Throughput (req/s) | CPU (avg cores) | CPU util % (of 8) | Throughput / core (req/s) |
| --- | ---: | ---: | ---: | ---: |
| Netty-Loom (this library) | 44584 | 2.19 | 27.4% | 20336 |
| Tomcat, platform threads | 3663 | 0.45 | 5.7% | 8069 |
| Tomcat, virtual threads | 26819 | 3.22 | 40.3% | 8322 |

Server-process CPU only (the k6 client is a separate process). **CPU (avg cores)** = Δ(cumulative CPU time) / Δ(wall clock) over the load window, so it counts only CPU burned while serving the load, not startup/JIT. **Throughput / core** is the discriminator: at 10,000 connections the client and server contend for the same 8 cores, so raw throughput partly reflects who grabbed more cores. Throughput-per-core is allocation-independent — a higher value means more requests served per core of work, an efficiency edge that should survive moving the client off-box. A target can post high throughput simply by pinning more cores; only a higher throughput-per-core says the win is structural.

## Memory per connection (under 10,000 concurrent connections) — unresolved, do not quote

**These are measurements, not a claim.** Netty-Loom's figure has risen across all three sweeps — 20.17 KB (2026-06-13) → 49.2 (2026-08-01) → 66.57 (here) — and neither increment is attributed. Two suspects, neither tested: the Security starter on the classpath, and NL-37's per-dispatch response buffering. Until issue **#144** resolves it, no memory-per-connection number from this file should be published.

| Target | Idle RSS (MB) | Loaded RSS median (MB) | Loaded RSS peak (MB) | Δ RSS median (MB) | Memory / connection (KB) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Netty-Loom (this library) | 236.8 | 886.9 | — | 650.1 | 66.57 |
| Tomcat, platform threads | 223.7 | 654.2 | — | 430.4 | 44.08 |
| Tomcat, virtual threads | 215.8 | 2235.1 | — | 2019.3 | 206.78 |

RSS includes committed heap, thread stacks, and Netty direct buffers. `Memory / connection = (loaded RSS median − idle RSS median) / connections`, using the steady-state median rather than the transient peak to suppress G1 heap-commit/JIT jitter (a ~100MB noise floor with `-Xmx2g` and no `-Xms`). At low connection counts this metric is noise-dominated and not meaningful; it only separates the targets once connections vastly outnumber the platform-thread pool (~200). Near-zero or negative values mean per-connection growth was below the noise floor — expected for virtual-thread targets whose parked continuations are cheap. Note the platform-thread target's footprint does **not** scale with offered connections: it caps at ~200 worker threads and refuses/queues the rest, so it can look memory-frugal while collapsing on latency and error rate above.
